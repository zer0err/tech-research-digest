# 研发与贡献流程

## 公开资产与本地资料

本仓库公开。源码、合成测试资料、公开需求、架构、贡献规范和发布内容随 Git 管理。内部排期、用户原话、角色分配、审查任务包、模型原始回复、未发布课程及原始日志保存在仓库外。

托管环境可在项目根目录用 repo、agents、tasks、logs 分别保存主仓库、本地角色配置、内部任务与日志；角色 worktree 可以由开发工具管理在其它位置。独立贡献者使用自己的本地目录即可，不依赖上述机器布局。凭据继续使用认证存储或环境配置。Git 忽略只防误添加，不构成访问控制，不能用强制添加绕过资料边界。

## 任务与角色

任务开始前，按 [任务模板](TASK_TEMPLATE.md) 明确目标、范围、唯一交付负责人、验收条件、基准 SHA 和预计路径。内部任务单在仓库外维护；GitHub issue、PR 只放适合公开的需求与交付摘要，不链接不可访问的本地文件。

产品角色负责目标与验收条件，项目角色负责依赖与交付，技术角色负责实现和技术风险，测试角色负责验证，视觉角色负责界面与交互，营销角色负责读者表达与转化依据。具体人员或代理分配由本地任务记录管理；按变更影响选择审查者，不要求所有角色逐一签字。

任务状态：待梳理 → 就绪 → 进行中 → 待审查 → 待验收 → 已完成。受阻时记录解除条件和可继续的工作；失败返回进行中。完成须逐项满足验收；发布属于任务目标时，还须有实际发布证据。

## 分支与 worktree

main 是整合基线，日常实现使用 feat/<任务编号>-主题、fix/... 或 docs/... 等任务分支。角色是协作职责，不是长期交付分支。一项任务默认一个交付分支；并行实现按不重叠的子任务拆分，并约定共享文件与接口整合顺序。

开始前检查 git status 和当前分支，保全已有修改后再切换；不盲目 stash 或重置其他任务。worktree 隔离工作目录和索引，共享 Git 对象与大部分引用，不能隔离私密提交。同一分支不强制在多个 worktree 同时检出。

审查固定提交 SHA。需要执行时使用审查者自己的干净目录或临时 worktree；不修改实现者目录。交接包括提交、路径、验证结果、限制与下一步。合入前核对最新 main，处理自动编辑产生的状态和页面变化，并对最终整合结果补充受影响检查。

迁移仓库或 worktree 后使用 git worktree repair 修复关联并验证。回收前确认已合入、无独有提交和未保存文件，另存被忽略的草稿与证据，再移除临时 worktree。开发工具管理的角色工作区由对应工具管理，不随任务完成自动删除。

## 按风险验证

- 文档和简单文案：链接、规则一致性及 git diff --check。
- 普通功能：受影响测试及相关角色审查；新增行为或缺陷修复补有价值的回归覆盖。
- 状态、调度、发布及共享逻辑：相关全量回归、技术影响审查、独立复核与恢复位置。
- 页面：按影响检查桌面、手机、关键操作和键盘；不能用样式源码替代视觉证据。

Python 检查使用 python -m pytest -q、ruff check .；浏览器脚本按现有 Node 测试执行。实际命令以依赖与测试文件为准。记录提交、环境、结果和覆盖范围，区分既存失败、环境缺失、本地测试、真实外部服务与线上验证。未执行项写明影响，避免无变化重复全量测试。

## 公开与发布

提交、PR 和 CI artifact 均按公开边界检查，不能把被忽略的报告直接视为可上传内容。只传必要且适合公开的结果；生产 reports 输出仍保留原运行入口，任务原始证据移至本地资料目录。state 中正式去重与发布回执按用途保留，不因整理而清空。

修改 docs 可能触发 Pages 发布，编辑工作流也会写入 main。合入和发布前核对实际工作流、授权和当前状态。已有授权持续有效；新增费用、对外行为或专项发布条件按对应要求处理。课程继续遵循发布前确认约定。

发布记录包含提交、工作流结果、访问与关键流程检查、限制和恢复位置。恢复正式状态前核对实际发布事实与通知回执，避免重复投递。任务完成后保留结论、必要证据和未解决事项，清理重复过程，按实际问题改进规则。

本流程是协作约定，不代表已经启用分支保护、自动门禁或完成独立审查。
